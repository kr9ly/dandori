# dandori-outline — プログラム設計

spike で前提が固まってから plan でマイルストーンを切るまでの間に、
**インターフェースを先行して確定し、核を擬似コードで書いて人間がレビューする**工程。

レビューの形は「構造をざっと眺めて違和感が出るか」であり、仕様の網羅確認ではない。
拾いたいのは**エージェントが見落としているもの・方針がずれているもの** — それらは
テストが緑でも残り、コードになってから直すと高くつく。

## この工程が存在する理由

他の全工程は、最終的に機械検査へ帰着する軸を扱う — B 行はテストで、不変条件は
呼び出し元の走査で、トレースは grep で検査できる。**可読性・再利用性・責務配置には
その帰着先がない**。良い設計と悪い設計を確実に見分けられるモデルがあるなら、そのモデルは
最初から良い方を書いている。見分けられないから書けないのであって、後段にレビューア
エージェントを足しても天井は上がらない（床は上がる — だから §3 の論点並べは残す）。

したがってこの工程の判定者は人間である。ユーザー接点を1つ増やしてでも置く理由は、
**判定を実装後に回すと最も高くつく**こと — 型・配置・責務の切り方は、やらなければ
コードレビューの時点で暗黙に決まってしまう決定であり、そこは気が変わるのに一番
高くつく瞬間である。擬似コードなら 100 行のオーダーで読め、間違っていても捨てる
コストがほぼゼロで済む。

**擬似コードで判定できるのはなぜか。** 可読性・再利用性は実質、インターフェースと
命名と責務配置の性質であり、実装本体にほとんど依存しないため。裏返すと、擬似コードに
書くべきは「実装すれば決まること」ではなく**「実装しても決まらないこと」** —
何をどこに置くか、何を名前にするか、何を分けて何をまとめるか。ループの回し方や
エラーメッセージの文面を擬似コードに書き込んでいたら、それは工程の対象を外している。

**擬似コードは契約ではない。** 実装時に判明した事実は既存経路（design.md の発見ログ）で
還流させる。outline.md と実装コードの突合チェッカーは作らない — 作ると、乖離の解消が
「実装を擬似コードに合わせる」方向に倒れ、還流の仕組みと喧嘩する。outline.md は
レビュー時点の合意の記録であって、実装が従うべき正ではない。

## 適用判定（skip できる条件）

フルコースの既定工程だが、**設計判断が薄いフィーチャーはスキップしてよい**。
判定は「実装しても決まらないことが残っているか」の一点:

- 既存の型・既存の置き場所への素直な追加で、新しい名前も新しい責務境界も生まれない
- design.md の「新規実装」が空、または既存パターンの機械的な複製のみ

これに該当するなら `outline.status: skipped` と理由を state.yaml に記録して plan へ進む。
迷ったら実施する（30 分の設計は数時間のレビューを節約する側に賭ける）。
短縮コース・dandori-lite にこの工程はない。

## 手順

### 1. インターフェースの確定（3点セット）

design.md（土台・改変箇所・新規実装・不変条件）を読み、以下を outline.md に書く。
既存コードの命名・イディオムに合わせること — `.dandori/resources.md` に規約があれば先に読む。

| 成果物 | 何を確定するか |
|--------|---------------|
| ファイル配置 | どのファイルが増え・変わり・消えるか（diff 構文）。ディレクトリの切り方はここで決まる |
| 型とシグネチャ | 主要な新規型と新関数の入出力。**呼び出し側から見た形**を書く（内部フィールドの列挙ではない） |
| コールスタック | 制御がどう流れるか。既存関数と新規関数の境界を明示する（変化が主眼なら diff 構文） |

**読み手を誘導する前置きは書かない。** 「ここを見てほしい」「ここは既存の踏襲」を
書き手が宣言すると、レビューアの目がそこに寄る。この工程で拾いたいのは
**書き手が見落としているもの・方針がずれているもの**なので、誘導は取りこぼしを増やす。
構造をそのまま置き、違和感が出るかどうかを読み手に委ねる。

**B 行の網羅はこの工程の関心事ではない。** 「どの仕様がどこで実装されるか」は plan.md の
マニフェストとカバレッジ検査の管轄であり、ここで併走させると裁定の議題が
「抜けている仕様はないか」に流れる。この工程が問うのは**インターフェースの良し悪し**
だけである。B-ID を注記として書くのは自由だが、書かなくてよい。

### 2. 核の擬似コード

**§1 で確定したインターフェースの呼び出し**として制御フローを書く。実装ではない。
目安は全体で 100 行前後 — 超えるなら書く対象を絞る。

- 分岐・早期リターン・エラーの送出先は書く（責務配置が現れる）
- ループ本体の詳細・文字列整形・型変換は書かない（実装すれば決まる）
- 呼ぶ既存関数は実在の名前で書く（架空の関数を呼ぶ擬似コードは再利用性を判定できない）
- 網羅は要らない。**判断が要る箇所だけ**書く（定型の CRUD、既存パターンの複製、
  設定の読み出しは書かない）。全経路を擬似コードにすると分量が読める限界を超え、
  人間のレビューが形骸化する。何を落としたかの説明も書かない — 落ちていることに
  違和感を持たれたら、それはそれで拾うべき論点である
- 状態モデルがある spec では、軸の分岐がどの関数に落ちているかが読めるように書く
  （design.md の「軸対応」で `[1箇所]` と宣言した軸が擬似コード上で散っていたら、
  そこが発見であり、この工程で拾うべき最大の獲物）

### 3. 論点並べ（サブエージェント1レーン）

**既存資産との照合**だけをサブエージェントに委譲する。これは既存コード検索であって
判定ではないため委譲できる — 責務の重複や再利用の機会は、コードベース全体を
見ないと気づけず、人間が短時間で網羅するのが最も苦手な部分である。

独立性ルールは他のレビュー工程と同じ（パスのみ渡す・要約や弁解を混ぜない・
**コンテキスト継承型のサブエージェント機構を使わない**）。

```
あなたは実装前のプログラム設計に対する調査係です。コードベースへの読み取りアクセスがあります。
設計案: <outline.md のパス>

以下の2点だけを、コードベースを検索して**論点として列挙**してください。
1. 重複: 設計案の各責務（新規型・新関数）について、同じ仕事をしている既存の型・関数・
   モジュールがコードベースに存在しないか。存在するなら所在（ファイル:行）と、
   どこまで同じでどこから違うかを書くこと
2. 再利用の機会: 設計案の各インターフェースについて、これを使えたはずの既存の
   呼び出し箇所が他にないか。あるなら所在と、現状のシグネチャでは使えない理由
   （引数が特化している / 依存が重い等）を書くこと

ルール:
- **採否の判断・推奨・良し悪しの評価をしないこと**。あなたの仕事は論点を並べることで、
  選ぶのは人間です。「〜すべき」「〜が望ましい」と書かない
- 各論点に所在（ファイル:行）を必ず付ける。所在を示せない論点は書かない
- 設計案の修正案を書かない
```

**この工程にレビューループはない。** 論点は1回並べて終わり、収束判定も台帳もない
（review / codereview の台帳機構は持ち込まない — あれは指摘の生死をラウンド間で
追跡する装置で、1回の裁定で閉じるこの工程には過剰）。

### 4. 人間裁定

論点をユーザーに提示し、1件ずつ裁定を受ける。裁定が定型（重複を許す / 統合する /
粒度を変える）なので、選択肢として提示する（ルーターの共通原則）。

- 裁定は**全件**が埋まるまで閉じない。空欄を残して plan へ進むと、その判断が
  実装後のコードレビューに繰り越される — この工程を置いた意味が消える
- 論点並べがゼロ件でも、outline.md 自体をユーザーに提示して承認を得る。
  設計案そのものへの指摘（命名が既存と揃っていない・分け方が細かすぎる等）は
  ここで受ける。**サブエージェントが見つけた論点だけが議題ではない**
- 裁定の結果 §1〜2 を書き直したら、論点並べはやり直さない（インターフェースが
  丸ごと別物になった場合のみ再走）

### 5. 確定

outline.md を書き出したら形式検査を実行し、exit 0 にする:

```
node <dandori-repo>/skills/dandori/scripts/dandori-docs.ts outline <spec.md> <design.md> <outline.md>
```

検査するのは4点だけ — 必須節（3点セット + 擬似コード + 論点と裁定）が揃っているか /
未裁定の論点が残っていないか /
design.md の「新規実装」とファイル配置の新規追加が片側だけになっていないか /
B-ID を注記したなら実在するか。
**擬似コードの中身も、B 行の網羅も検査しない**。この工程が扱うのは機械検査に
原理的に載らない軸であり、検査を厚くすると「検査が通った = 設計が良い」という
誤読を招く。緑は「議題が全部閉じた」以上の意味を持たない。
その上で state.yaml を更新する。

## 完了条件

- outline.md が存在し、形式検査（`dandori-docs.ts outline`）が exit 0
- 「論点と裁定」の裁定列が全件埋まっている（論点ゼロなら表は空でよいが、
  outline.md 自体のユーザー承認は必要）
- 裁定の結果 spec / design に還流するものがあれば反映済み
  （spec の振る舞いに波及するものはユーザー裁定を経る。design の改変箇所・新規実装・
  軸対応の書き換えは還流してよい — outline は design の一段下であり、
  下で決まった配置が上の記述を古くする）
- state.yaml: `phase: plan`、`phases_done` に outline 追加、`outline.status: done`
  （skip 時は `skipped` + 理由。どちらでも `phases_done` には入る）
