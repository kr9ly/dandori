# dandori-lite — 段取りのエッセンスだけ

覚えることは 2 つだけ。**「何が満たされればゴールか」を「何で検証するか」と同時に書く**、
そして**最後に全行を照合して、未検証を黙って通さない**。

これで防げるのは「動いた気がするが仕様を満たしていない」実装と、エラーパスの取りこぼし。
成果物は `spec.md` 1 枚（トレース表も同じファイルの末尾）。フル版（`dandori` ルーター）の
16 工程・複数ドキュメント・指摘台帳は使わない — 足りなくなってから足す（末尾の表）。

## 手順

### 1. 仕様を書く（ゲートタグつき）

`spec.md` を作る。形式は下記。書くときのルールは 3 つ:

- **検証不能な要件を書かない**。「使いやすい」「高速」が出たら、観測できる条件
  （操作列と期待結果、数値閾値）に言い換える。言い換えられないものはゴールから外す
- **各行に検証手段のタグを付ける** — `unit` / `e2e` / `manual`（人間の目視・手動操作）。
  タグは検証コストの申告。`manual` が多すぎたら自動化できる形への言い換えを考える
- **異常系はマトリクスから出す**。「ありそうなエラー」を直感で挙げるのではなく、
  結果に影響する**状態変数**を列挙し（ログイン有無・ネットワーク・データの空/満杯・権限・
  事前操作の有無）、**各変数 × 正常系シナリオ**を機械的に走査して挙動が変わる交点を拾う。
  ここをサボると必ずエラーパスが漏れる

ユーザーと確認してから次へ進む（ここが唯一の壁打ち — 以降は自律で進めてよい）。

### 2. 前提を 1 つ確かめる

実装前に、**外れたとき一番痛い前提**を 1 つ選んで**実際に動かして**確かめる。
既存テストを走らせる、使い捨てスクリプトで関数を直接呼ぶ、アプリを起動して該当パスを通す
— どれでもよい。コードを読んだだけの前提は当たり前に外れる。

`spec.md` の「前提の確認」節に、確かめた前提と**まだ確かめていない前提**を書き分ける:

| マーク | 意味 |
|--------|------|
| `[実行検証済]` | 動かして確認した。**実行コマンドと観測結果**を併記する |
| `[読解のみ]` | コードを読んだだけ。実行できない理由を併記する |

「実行できない理由」が単なる手間なら実行する。`[読解のみ]` が残るのは構わない —
**等級が付いていること**が目的で、全部を検証することではない。

### 3. 実装する

- **テストの名前に B 行 ID を入れる**（例: `test("B-3: 在庫ゼロは 409 を返す", ...)`）。
  ステップ 4 の照合が grep で済む
- **テストを通すためにテスト側を弱めない**
- **規定のない回復分岐を書かない**。異常・欠損・想定外の入力を検出して**処理を継続する**
  分岐（代替値での続行・沈黙スキップ・握りつぶし・暗黙のデフォルト応答）は、その振る舞いを
  規定する B 行があるときだけ書く。無ければエラーをそのまま送出し、仕様の穴として報告する
  — 気を利かせたフォールバックは、想定外を沈黙のうちに劣化させる

### 4. 全行トレースして裁定する

`spec.md` の末尾にトレース表を作り、**全 B 行**の検証状況を埋める。
`unit` / `e2e` は**この時点で再実行する**（実装中の「通りました」を根拠に流用しない）。

| 状態 | 意味 |
|------|------|
| ✅ passed | 検証した（根拠: テスト名・実行出力） |
| ⏳ 確認待ち | `manual` 行。確認手順を書いてユーザーに出す |
| ⚠️ 未検証 | 対応するテストが無い |
| ❌ failed | 落ちている |

**⚠️ と ❌ を黙って通さない**のがこの工程の全部。残ったら分類して裁定する:

- **実装バグ** → 直してトレースを最初からやり直す
- **前提の欠落**（仕様が現実と合っていなかった）→ 仕様を直す。ステップ 1 に戻る
- **検証手段がない** → テストを追加するか、ユーザー承認の上で `manual` に落とす。
  **黙認は不可**

全行 ✅（またはユーザーが明示的に受け入れた）でコミット。

## spec.md の形（この 1 枚だけ）

```markdown
# <機能名> 仕様

## ゴール
<1〜3文> + 満たすべき観測可能な条件の箇条書き

## スコープ外
- <やらないこと。後からのスコープクリープを止める防波堤>

## 前提の確認
- <前提>: <何に使うか> [実行検証済: `<コマンド>` — <観測結果>]
- <前提>: <何に使うか> [読解のみ: <実行できない理由>]

## 振る舞い仕様

### B-1: <タイトル>
- Given: <前提状態。具体値は境界値を選ぶ — 0/1/複数・空文字/null/欠落>
- When: <操作・入力>
- Then: <観測可能な期待結果>
- Gate: unit

### B-2: ...（異常系も同形式。Given に異常状態を置く）

## 未解決事項
- <確定しなかった点。実装までに解消するか、明示的にスコープ外へ>

## トレース表

| B 行 | ゲート | 状態 | 根拠 |
|------|--------|------|------|
| B-1 | unit | ✅ passed | <テスト名 / 実行出力> |
| B-2 | manual | ⏳ 確認待ち | 確認手順: ... |
```

B 行の ID は追加は末尾、削除は取り消し線 + 理由（`### ~~B-3: ...~~`）。
**番号を振り直さない** — 振り直すとトレース表と対応が取れなくなる。

## 機械検査（任意）

形式が崩れていないかを機械で確認できる（このリポジトリが手元にあり、Node 22.18+ の場合）:

```bash
node <dandori-repo>/skills/dandori/scripts/dandori-docs.ts spec <spec.md>
```

必須セクションの欠落・B 行のフィールド漏れ・ゲートタグの語彙外・ID の重複や欠番を検出する。
上の形式のまま書けば通る（トレース表を同居させても通る）。

## 足りなくなったら — フル版の工程を足す

軽量版は劣化版ではなく**起点**。痛みが出た箇所だけ足していけばよい。

| 出た痛み | 足す工程 |
|----------|----------|
| 実装前に立てた前提が外れて手戻りした | `dandori-ground`（全前提の等級づけ）+ `dandori-spike`（最高リスク前提の実地検証） |
| 仕様の穴が実装中に次々出てくる | `dandori-review`（独立レビューア + 反証フェーズ。仕様と設計を第三者検証する） |
| 実装エージェントが制約を読み飛ばす | `dandori-plan`（マイルストーンごとの部分開示マニフェスト） |
| テストは緑なのにバグが出た | `dandori-codereview`（テストが検証できない領域を5レーンで潰す） |
| 状態変数の組み合わせが多すぎて手で追えない | 状態モデル（`docs/appendix-state-model.md` — 直積の機械走査） |
| デザイン指示の外の画面が巻き添えで変わった | `dandori-sketch`（画面を変更/不可侵に全数分類） |
| 仕様書がコードと乖離して嘘をつき始めた | `dandori-annotate` → `dandori-strip` → `dandori-cleanup`（判断を残して文書を処分する） |

全体像とそれぞれの理由は `README.md` と `docs/digest.md`（工程ごとに一行）。
フル版に移るときは `dandori` ルーターに切り替える — この `spec.md` はそのまま使える
（フル版の spec.md と同じ形式。トレース表だけ `trace.md` に分かれる）。

## 完了条件

- `spec.md` の全 B 行にゲートタグが付いている
- 前提の確認節に、確かめた前提と未確認の前提が等級つきで書かれている
- トレース表の全行が ✅、またはユーザーが明示的に受け入れている
- コミット済み
