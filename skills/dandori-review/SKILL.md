# dandori-review — 独立レビューループ

仕様と設計を第三者視点で検証する工程。レビューアの独立性が品質の源泉なので、
**メインエージェントの解釈・補足・弁解をレビューアに一切渡さない**。

## 独立性の担保（厳守）

- サブエージェントには **ファイルパスだけ**を渡す（そのレーンが照合先とするものに限る —
  spec.md / design.md の両方か、片方か）。プロンプトに内容の要約・言い換え・背景説明を
  埋め込まない（無意識の答え合わせ・バイアス注入を防ぐ）
- **コンテキスト継承型のサブエージェント機構を使わない**（親の会話履歴を引き継ぐ fork 型の
  起動）。渡す情報を絞る意味がなくなり、メインの仮説・調査結果・弁解がまるごとレビューアに
  入る — プロンプトに何も書かなくても独立性が失われるため、事故が観測できない形で起きる。
  レビューアは常に新規コンテキストで起動する
- 調査して初めて分かった原因、メインエージェントの仮説、「ここは意図的にこうした」等の
  弁解は渡さない
- レビューアはコードベースへの読み取りアクセスを持つ（検証に必要）
- `.dandori/resources.md`（リソースマップ）に規約・設計ドキュメント・バグパターン集が
  あれば、その**ファイルパスを**指示に追加してよい（レビュー観点の項目として列挙する）。
  内容の要約・抜粋は渡さない — 要約はメインエージェントの解釈を混入させる

## 観点別レーンの並列ディスパッチ

観点 × 照合先で分割したレーンを、それぞれ**独立のサブエージェント**として並列起動する。
1 体に全観点を持たせる構成はやめた — 毎ラウンド「そのとき目に入った場所」から指摘が出て、
直列ラウンド数が伸びる（実測では収束まで 4〜10+ ラウンドかかり、生存件数が単調減少せず
新規指摘が湧き続けた。網羅ではなくサンプリングの挙動）。レーンごとの問いを狭くして
1 ラウンドの発見量を上げ、直列ステップを削る — codereview と同じ構造。

| レーン | 渡すもの | 問い |
|--------|----------|------|
| 要件充足・整合性 | spec.md + design.md | この設計を実装しても spec のゴールを満たさない箇所はないか / spec と design の矛盾、design が触ると言っていない箇所への隠れた影響 |
| エラーパス | **spec.md のみ** | 状態変数の洗い出しに漏れはないか。コードに実在する失敗経路（例外・早期 return・外部呼び出しの失敗・トランザクション境界・並行更新）を全数列挙し、対応する B 行があるか突合せよ |
| 前提の監査 | **design.md のみ** | 土台・不変条件の主張をコードで検証。`[読解のみ]` を重点的に疑い、`[実行検証済]` は証拠形式を監査してコマンドを再実行する（併記なし・再現しないものはマークの降格を指摘） |
| 同値分割 | spec.md | 軸・Given の値域を同値分割として監査 — クラス漏れ / クラス内非一様性（**多重度の罠**: 複数候補から 1 件を選ぶ処理は選択順序が観測可能な仕様で、単数クラスと同値ではない）/ 境界値の 3 態 |
| モデル監査（モデルがある spec のみ） | spec.md | モデルが**原理的に検出できない型**（軸内の逐次連鎖 / 分類述語の値域の穴 / 未発見の状態変数 / 値内部のセマンティクス / エラー優先順位）+ **直交宣言の監査** |
| 規約・既知パターン照合（resources.md に該当ドキュメントがある場合のみ） | spec.md + design.md + 規約のパス | 規約違反・既知の失敗パターンへの該当。内容の要約は渡さず、レビューアに読ませる |

**渡さないものが観点を作っている**:

- エラーパスレーンに design を渡さない — 設計の言い分を知ると「design に書いてあるから
  大丈夫」の追認が入る。エラーパスは spec の異常系とコードの現物から逆算するのが正
- 前提の監査レーンに spec を渡さない — 前提の真偽は仕様ではなくコードとの照合で決まる。
  仕様を知ると「仕様どおりだから前提も正しいはず」の追認が入る

**直交宣言の監査**（モデル監査レーン）が第三者検査点として要るのは、チェッカーが強制するのが
裁定の**存在**であって正しさではないため — 「裁定のふり」（チェッカーを黙らせるためだけの
吟味なし直交宣言）はチェッカー自身には検出できない。reason が spec 本文から導けるかを検証し、
本文に根拠のない reason はそれ自体を指摘する（major・ground 送りへの差し戻し）。
反例となる交点が見つかれば依存宣言への昇格 + 交点 B 行の追加（blocker）。
同値分割の技法は `docs/appendix-test-design.md` §1、モデルの検出限界は
`docs/appendix-state-model.md` の「検出できないもの」を参照。

共通テンプレート（レーン固有の渡すものと問いを差し替える）:

```
あなたは実装ドキュメントの独立レビューアです。以下を読み、批評してください。
<レーン固有: 渡すファイルのパス>

<レーン固有: 観点>

各指摘に深刻度を付けること:
- blocker: 要件を満たさない実装になる / 前提が事実と異なる
- major: エラーパス・状態変数の欠落、不変条件の見落とし
- minor: 改善提案・表現の曖昧さ

ルール（あなたは発見係 — 指摘の白黒は後段の独立反証フェーズが付ける）:
- 見落としは反証フェーズでは回復できないが、偽陽性は反証フェーズが破棄できる。
  疑いは自己検閲せず列挙すること。「確信が持てないから黙る」は禁止
- 照合対象をまず全数列挙し、1 件ずつ疑いを探すこと。目についた 1 件で走査を止めない
- 深刻度は「指摘が真だった場合」の深刻度で付ける。確信度で下げない
- minor だけは反証フェーズを通らずユーザーに直接届くため、確信のあるもののみ報告すること
- **自分のレーンの観点に集中すること**。他観点の疑いが目に入っても深追いしない
  （並列の別レーンが同じ spec / design を別の観点で走査している）

出力: 深刻度別の指摘リスト（各指摘に根拠となるファイル:行と、可能なら
「何を確認すれば白黒つくか」を付ける）
```

レーンの重複指摘は台帳の同一論点照合が落とす（同一 Rd の同一論点は追記されない）。
各ラウンドは全レーンを再走する — 反映で spec / design 全体が書き換わるため、
codereview のような「修正に関係するレーンだけ」の絞り込みはしない。

## 指摘台帳（review-ledger.md）

全指摘を `.dandori/specs/<feature>/review-ledger.md` に永続化する。会話にしか存在しない
指摘（特に**却下したもの**）を作らないため、また収束判定（再燃・振動）を記憶と裁量でなく
**台帳との照合**という機械的作業に落とすため。dandori-codereview と共用
（ID 接頭辞で区別: この工程は `R-n`、codereview は `C-n`）。

```markdown
| ID | Rd | 深刻度 | 論点（一行） | 処置 | 根拠・理由 |
|----|----|--------|--------------|------|-----------|
| R-1 | 1 | blocker | B-3 の Given が既存 API の実挙動と矛盾 | 反映済 | design.md 土台節を修正 |
| R-2 | 1 | major | 在庫ゼロ×クーポンの交点 B 行がない | 却下 | スコープ外（spec §外）— ユーザー裁定 |
| R-3 | 2 | major | R-1 と同根: 修正後も戻り値の型が不一致 | 再燃→R-1 | escalate 判定の材料 |
```

- 処置の語彙: `反映済` / `却下`（理由必須） / `保留`（minor の採否待ち） / `再燃→<ID>` /
  `反証破棄`（反証根拠必須。R/C 共通語彙）。
  **この 5 語以外を書かない**（「対応済」「修正済」等の言い換えは checker の語彙検査に落ち
  escalated を誘発する）。裁定・補足の注記は処置セルに併記せず
  根拠・理由セルに書く — メインが裁定を記録するときも同じ
- セル内に `|` を書くときは `\|` でエスケープする（型のユニオン表記 `'active' \| 'closed'` 等 —
  生の `|` は列区切りと解釈され、列数エラー・欠番誤検出を連鎖させる）
- **保留の滞留弁**: 理由セルが空の保留（採否待ち）が 2 ラウンド以上放置されると
  チェッカー（L6）が指摘し passed を塞ぐ — 放置された保留論点は後続ラウンドで major として
  再指摘され escalate を招く。ユーザー裁定で保留のまま残す場合は理由セルに
  裁定を書く（理由付き保留は採否確定済みとして検査対象外）
- **裁定の明文化**: ユーザー裁定（却下・一般裁定）は台帳に記録するだけでは再指摘を止められない —
  各ラウンドのレビューアは台帳を読まない（情報隔離の設計上の帰結）。裁定は適用対象の近傍
  （spec の B 行注記・design の該当節）に明文化すること。複数箇所に適用される一般裁定は
  **初回で全適用箇所に書き切る** — 逐次展開は「直した箇所以外への再指摘」の振動を生む
- **再燃の解消**: `再燃→<ID>` はユーザー裁定で振動の原因（処置側の誤り or レビューアの過剰検出）を
  決着させたら、処置を `反映済` に更新し理由セルに「再燃→<ID> として検出 → 裁定で解消」と経緯を残す。
  処置列に `再燃→` が残っている行だけが escalate を駆動する — 解消済み再燃を残置すると
  収束判定が永遠に escalated を返す
- ラウンドごとに、受け取った指摘を**まず全件台帳に追記してから**処置に入る。
  その際、既存行と同一論点かを照合し、同一なら新規行にせず `再燃→<ID>` を記録する
- **行の追記は手編集でなくチェッカーの `ledger-append` で行う**（決定的・冪等。R/C/F 共通）:

  ```
  node <dandori-repo>/skills/dandori/scripts/dandori-docs.ts ledger-append <review-ledger.md> \
    --prefix R --rd <ラウンド> --rows-stdin <<'JSON'
  [{"index":0,"severity":"minor","topic":"論点の一行","action":"保留","reason":"spec §3"}]
  JSON
  ```

  ID 発番・行の書式・処置語彙・書き先パスがコマンド側で固定される。追記をエージェントに
  任せる設計では、発番した ID の行が台帳に書かれない書き落ち（欠番化）・worktree 内複製への
  二重書き込み・ラウンドを跨いだ ID 再採番衝突が、プロンプト強化を重ねても再発した
  。同一 Rd に同一論点の行があれば追記せず既存 ID を返す（冪等）。
  エージェントの仕事は**既存行との同一論点照合だけ**（台帳ファイルは読み取りのみ）
- **指摘ゼロのラウンドの記録**: 行を追記しなかったラウンドは
  `<!-- round: R Rd=7 指摘なし -->` 形式のマーカー行を台帳末尾に追記してから収束判定を
  実行する（codereview は接頭辞 `C`）。行が残らないラウンドはチェッカーから観測できず、
  過去の停滞パターンから escalated を返し続ける。blocker / major の行を追記した
  ラウンドでは不要。追記は手編集でなく収束判定コマンドに
  `--mark-zero-round R auto` を付けて行う（決定的・冪等 — エージェントによるマーカーの
  自由編集は監査改竄と誤検知されてブロックされる）。ラウンド番号は `auto`
  （台帳の実ラウンド番号 = 行と既存マーカーの最大 Rd から導出）で渡す — 工程側のローカルな
  数え上げを渡すと台帳の Rd 系列と食い違うマーカーが打たれ、収束済みなのに escalated に
  なる。明示の番号を渡すのは台帳の Rd を自分で確認したときだけ

## ループの回し方

1. **観点別レーンを並列起動し**、全レーンの指摘をマージして受け取る
2. **全指摘を台帳に追記する**（既存行との照合込み — 上記）
3. **blocker / major を指摘ごとに独立の反証エージェントで精査する**（finder/verifier 分離）。反証エージェントには指摘 1 件と spec/design のパスだけを渡し、
   事実誤認・既カバー・既裁定（precedents）・到達不能を原典で確認させる。
   **「到達不能」を反証根拠にする場合はデータ由来の到達可能性（nullable カラム・
   スキーマ変更前から残る古いレコード・部分書き込み）の確認を必須にする** — 型注釈や
   現行コードパスのみを根拠にした断定は誤反証を生む。
   反証成立 → 台帳の処置を `反証破棄`（反証根拠必須）。確定不能は生存（安全側）。
   レビューアは recall 優先（自己検閲禁止）で、精度はこのフェーズが全面的に担う
4. **反証を生き残った blocker / major をドキュメントに反映する**。反映は自分で判断できるものは自律で行い、
   spec の意図に関わるもの（ゴール定義・スコープの変更を伴うもの）はユーザーに裁定を仰ぐ。
   処置を台帳に記録する
5. minor は一括でユーザーに提示し、採否をまとめて決める（ループの駆動源にはしない。
   minor は反証フェーズを通らない — レビューアに「確信のあるもののみ」を要求する）。
   提示前に台帳の既存論点と照合し、**重複する minor は行を追加せず再提示もしない**
   （反証・重複照合を通らない minor は、同一論点が素通しでユーザーに重複して届く。
   workflow は台帳記録係の照合で機械的に落とす）
6. 反映後、**新しいサブエージェントの全レーン**で再レビュー（前ラウンドの記憶を
   持たせない。台帳もレビューアには渡さない — 前ラウンドの結論による先入観を防ぐ）
7. state.yaml の `review.rounds` をインクリメント

### 収束条件

台帳から機械的に判定する。判定はチェッカーが機械化している —
`node <dandori-repo>/skills/dandori/scripts/dandori-docs.ts ledger <review-ledger.md>`
がラウンド推移と判定（passed / escalated / 継続）を出力し、あわせて台帳の形式
（未処置の行・理由なし却下・保留の誤用・保留の滞留・再燃参照切れ・ID 重複/欠番）を検査する。
各ラウンドの処置記録後に実行する。判定基準:

- **通過**: 反証を生き残る blocker / major がゼロのラウンド（発見ゼロ・全件反証破棄の両方を含む）が出たら通過。`review.status: passed`。
  blocker / major が残っている状態でのラウンド数による打ち切りはしない
- **escalate（脱出弁）**: ラウンド数ではなく**収束の兆候の消失**で判定する。以下のいずれかに該当したら
  `review.status: escalated` にしてユーザーに裁定を仰ぐ:
  - 台帳に `再燃→` が付いた（反映済の論点が後続ラウンドで再指摘され**反証も生き残った** —
    レビューアと反映の間で解釈が振動している。反証で破棄された再指摘は偽陽性の再生産であり再燃ではない。
    `再燃→` の参照が連鎖する場合はチェッカーが終端まで辿り、終端の再生産が反証破棄なら
    解消済みとして除外する — 裁定済み論点の再生産が破棄され続けているのは収束）
  - 3ラウンド以上連続で blocker+major の件数が減っておらず、**かつ最新ラウンドに未解消の
    再燃が含まれる**（台帳の Rd 列で数える。件数の非減少だけでは「毎ラウンド異なる新規の
    事実発見が続く健全な収束過程」と振動を区別できない）
  （典型: 要件自体が曖昧 → spec に差し戻し / レビューアが過剰検出 → 指摘を却下して通過扱い）
- 各ラウンドの新規指摘が「未知の事実の発見」である限りは健全な収束過程 — ラウンドを継続する

## Workflow スクリプト（任意 — 対応環境のみ）

このループ（レーン並列レビュー → 台帳追記 → 反証 → 反映 → 収束判定）は決定的なので、
サブエージェントのオーケストレーション機構（Claude Code の Workflow ツール等）が使える
環境では、同梱の `workflow.js`（このスキルと同じディレクトリ）で機械駆動してよい。
利益は独立性ルールの構造的な強制 — 「レビューアにはパスだけを渡す」「台帳を渡さない」
「各ラウンドは新しいレビューア」「レーンごとに渡すものを絞る（エラーパスに design を、
前提の監査に spec を渡さない）」がプロンプトテンプレートに固定され、実行のたびの
自制に依存しなくなる。

- args: `specDir`（specs/<feature>）/ `checkDocs`（dandori-docs.ts の実行プレフィックス）、
  任意で `reviewDocs`（観点に加える参照ドキュメントのパス配列）/
  `checkStateModel`（check-state-model.ts の実行プレフィックス — 状態モデルつき spec では
  **必ず渡す**。反映エージェントが反映後にチェッカーを exit 0 まで回すことを強制し、
  軸値未定義・Covers 未知値・単軸 dependent 等の形式エラーの持ち込みを工程内で検出する）/
  `maxRounds` / `workRoot` / `models` / `efforts`。
  JSON オブジェクトで渡す（ハーネスによっては文字列で届くが、スクリプト側で JSON.parse に
  正規化される — 失敗時は `args に specDir / checkDocs が必要` エラー）
- `models` / `efforts`: 役割別のモデル・reasoning effort の上書き（役割語彙は
  finder / refute / fix / brief / triage / scribe / judge / mech の 8 語で 4 workflow 共通）。
  この工程のレーン（`finder`）と反映（`fix`）は既定でモデル未指定 = メインからの継承 —
  仕様・設計の批評はこの工程の品質の源泉なので下げない。**反証（`refute`）の既定は Sonnet
  なので、精度ゲートとしてはメイン相当への引き上げを検討する**（`{"models":{"refute":"opus"}}`）。
  レーンは 4〜6 本が並列で走るため、`finder` を上げるとラウンドあたりのコストが
  レーン数倍で効く — 直列ラウンド数の削減とのトレードオフで決める
- `workRoot`: 検証対象コードの作業ルート。worktree 並列レーン等、コードがセッションの
  主作業ディレクトリと別の場所にあるとき指定する（サブエージェントは主作業ディレクトリで
  動くため、指定しないと相対パスの探索が空振りし、他 worktree のコードを検証対象と
  取り違えるリスクがある）。レビューア・反証エージェントのプロンプトに参照先の固定として
  注入される。**workRoot 指定時は `specDir` と `reviewDocs` を絶対パスで渡すこと**
  （スクリプトが検査して弾く）— 台帳・spec は閉じ込めの適用除外としてプロンプトに明示注入される
  （除外がないと worktree 内に台帳の複製が作られ、書き先が分裂する）。
  相対パスの reviewDocs は workRoot で作業するエージェントから解決できず、規約・バグパターン
  照合の観点が黙って欠落する
- 収束判定の verdict はチェッカー出力の `[verdict] R=<token>` 行から**スクリプト側で決定的に
  マッピング**する — 判定エージェントの仕事は同行の逐語転記のみ（意味的マッピングをさせると
  「継続」を escalated に誤対応づける事故が起きる）
- 台帳への行追記も同型に縮退している: 照合エージェント（同一論点の判定のみ・台帳は読み取り専用）→
  スクリプトが行データを構築 → 追記エージェントは `ledger-append` コマンドの実行と
  `[appended] index=<i> id=<ID>` 行の逐語転記のみ。行 ID の出所はコマンド出力だけで、
  エージェントが ID を発番・推測する経路がない
- 戻り値は `passed` / `escalated`（再燃 / 停滞）/ `max_rounds`（ラウンド上限での打ち切り —
  収束の失敗ではない。生存指摘は反映済みで、続行するか収束とみなすかのユーザー裁定に返る）/
  `needs_adjudication` / `blocked`。**裁定はスクリプト内で解決しない** — spec の意図に関わる指摘と「指摘の却下」は `needs_adjudication` で返る。
  minor の採否・却下の台帳記録・state.yaml の更新は本文の該当節に従ってメインが処理し、
  裁定後に**新規実行**すれば台帳の Rd から次ラウンドとして再開される
- **再開に resume（resumeFromRunId 等のキャッシュ再生機構）を使わない**。このスクリプトの
  プロンプトは同一入力なら不変のため、resume では全エージェント呼び出しがキャッシュ再生され、
  ディスク（台帳・spec/design）を読み直さずに旧ラウンドの結果をそのまま返す。継続状態は台帳が
  ディスク上で保持しており、新規実行の入口確認が次ラウンド番号を台帳から導出する —
  新規実行が正しい再開手段であり、resume に利点はない
- 使えない環境では本文の手順をそのまま手で回す。挙動は同一（スクリプトは本文の写しであり、
  乖離したら本文が正）
