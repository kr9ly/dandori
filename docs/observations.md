# 実戦観測ログ — 規約の出所

各 SKILL の規約が「どの事故から来たか」の記録。**工程の実行時に読む必要はない** —
規約とその理由（因果の一句）は SKILL 本文にある。この文書を開くのは、規約を変えたい・
外したい・緩めたいときだけ。「なぜこんな面倒な縛りがあるのか」への回答がここにある。

分離の理由: 規約と、規約を生んだ事故の記録は寿命が違う。前者は工程ごとに毎回読まれ、
後者は改定のときだけ読まれる。同じ場所に置くと、実行時に読む量が根拠の分だけ膨らむ
（dandori 自身の annotate の原則 — 判断の由来を実行時の動線に置かない — の自己適用）。

各項目は「規約 → 観測」の順。日付は事故の観測日。詳細な対応内容は同日前後の
コミットメッセージが正。

## 台帳（review-ledger.md）

### 行追記をエージェントの Edit から外し、`ledger-append` に固定した

2026-07-25 恒久対策。追記をエージェントに任せる設計では、プロンプトの強化を重ねても
次の 3 症状が再発し続けた:

- 発番した ID の行が台帳に書かれない書き落ち（C-2 / C-31 の欠番化）
- worktree 内の複製へ書き込む台帳二重化（正準側が部分台帳になる）
- ラウンドを跨いだ ID の再採番衝突

書き込みを Edit から外すのが唯一の根治で、エージェントに残したのは既存行との
同一論点照合だけ（台帳ファイルは読み取り専用）。

### 「指摘なし」マーカーの追記を `--mark-zero-round` に固定した

2026-07-21。エージェントによるマーカーの自由編集が、監査改竄と誤検知されて
ブロックされた実績がある。

### マーカーのラウンド番号は `auto` で渡す

2026-07-25 実戦観測。工程側のローカルな数え上げを渡した結果、台帳の Rd 系列と
食い違うマーカーが打たれ、収束済みなのに escalated を返し続けた。

### 処置の語彙を 5 語に固定した（言い換え禁止）

2026-07-23 実戦観測。「対応済」「修正済」等の言い換えがチェッカーの語彙検査に落ち、
escalated を誘発した。

### 保留の滞留弁（L6）

実戦観測。理由セルが空の保留（採否待ち）を放置すると、後続ラウンドで major として
再指摘され escalate を招いた。

### 裁定は初回で全適用箇所に書き切る

実戦観測。逐次展開すると「直した箇所以外への再指摘」の振動が起きた。

## 収束判定

### verdict はチェッカー出力の逐語転記 + スクリプト側の決定的マッピングにした

2026-07-22 実戦観測（codereview 側）。判定エージェントに意味的マッピングをさせた結果、
「継続」を escalated に誤対応づける事故が起きた。

### 停滞判定に「未解消の再燃」の条件を加えた

2026-07-10 改定。件数の非減少だけでは、「毎ラウンド異なる新規の事実発見が続く健全な
収束過程」と解釈の振動を区別できなかった。

### ラウンド数による打ち切りをしない（review）

2026-07-04 ユーザー裁定。blocker / major が残っている状態での打ち切りは、
未解決を残したまま通過させることになる。

### maxRounds 到達を escalated と分けて `max_rounds` で返す

2026-07-25 実戦観測。混ぜると、収束しているのに「解釈が振動している」と読める報告に
なった。生存指摘は修正済み・ゲート緑・次ラウンドの再レビュー前という状態なので、
判定前の打ち切りとして扱うのが正しい。

### 反証フェーズの導入（review 側）

2026-07-09。レビューアの過剰検出がノイズで溢れ、ループが収束しなくなった。
codereview に先に入れていた finder / verifier 分離を review にも展開した。

### 「到達不能」を反証根拠にする場合はデータ由来の到達可能性を確認させる

実測。型注釈や現行コードパスのみを根拠に到達不能と断定し、誤って反証した事例があった
（nullable なカラム、スキーマ変更前から残る古いレコード、部分書き込み、外部入力）。

### minor の重複照合を台帳記録係に寄せた

実測。反証・重複照合を通らない minor は、同一論点が素通しでユーザーに重複して届いた。

## レビューの経済（recall と precision の分離）

### review を 1 体の全観点レビューアから観点別の並列レーンに変えた

2026-07-25、過去 5 フィーチャーの台帳（現存分）のラウンド推移を集計した結果:

```
cart-userinfo         Rd1=1 → Rd2=2 → Rd3=2 → Rd4=0                            （4 ラウンド）
payjp-charge          Rd1=2 → Rd2=1 → Rd3=1 → Rd4=1 → Rd5=1 → Rd6=1 → Rd7=0    （7）
gift-product-cancel   Rd1=3 → Rd2=1 → Rd3=3 → Rd4=2 → Rd5=1 → Rd6=4 → Rd7=4 → Rd8=0（8）
admin-gift-product    Rd1=3 → Rd2=5 → Rd3=4 → Rd4=5 → Rd5=2 → Rd6=2 → Rd7=1 → Rd8=3 → Rd9=3 → …（10+）
yurumaru-gift-product Rd1=2 → Rd2=3 → Rd3=3 → Rd4=3 → Rd5=2 → Rd6=4 → Rd7=2 → Rd8=3 → Rd9=3 → …（10+）
```

生存件数（blocker+major）が**単調減少していない** — 毎ラウンド新規指摘が湧き続けている。
「毎ラウンド 1 件ずつ 6 回」（payjp-charge）や「Rd5=1 → Rd6=4」（gift-product-cancel）は、
網羅の進行ではなく**サンプリング**の挙動に見える。

構造的な原因の仮説: review は 1 体が 4 観点 + 状態モデル監査 + 同値分割監査 + 直交宣言監査を
すべて受け持っていた（codereview は 5 レーン並列で各レーンの問いが狭い）。長大なプロンプトを
渡された 1 体は、毎ラウンド新規コンテキストで「そのとき目に入った場所」を見るため、
毎回違う場所から指摘が出て直列ラウンド数が伸びる。

対策として観点別レーン（要件充足・整合性 / エラーパス / 前提の監査 / 同値分割 /
モデル監査 / 規約照合）の並列化に変えた。あわせて「渡さないもの」で観点を作っている —
エラーパスレーンに design を渡さない（設計の言い分を知ると追認が入る）、前提の監査レーンに
spec を渡さない（前提の真偽はコードとの照合で決まる）。

**効果は未測定**（次フィーチャーで収束までのラウンド数を比較する）。レーン数倍のコストが
直列ラウンド数の削減で回収できるかが検証点。

### レーンに recall を、反証に precision を求める

2026-07-08 実測。精度をレーンに求めた結果、自己検閲が起きて反証フェーズが飢えた —
4 レーンの生報告が計 blocker/major 1 件・minor 2 件・反証破棄 0 で、反証フェーズに
仕事がない状態のまま「毎ラウンド major 1 件」のプラトーが続いた。

## workRoot（コードが別ディレクトリにある構成）

### 台帳・spec を閉じ込めの適用除外としてプロンプトに明示注入する

2026-07-22 実戦観測。除外を明示しないと一部のエージェントが worktree 内に台帳の複製を
作り、ラウンドごとに書き先が分裂して、収束判定が正準側の部分台帳だけを見て escalated
まで空転した。

### workRoot 指定時は specDir / resources / reviewDocs を絶対パスで要求する

2026-07-23 実戦観測。相対パスは「cd workRoot して作業する」エージェントから解決できず、
周辺整合レーンの規約照合が黙って欠落した。

### args の型を明示検査する

2026-07-25 実戦観測。単一パス想定の args（resources）に配列を渡した結果、絶対パスガードが
`.startsWith is not a function` でクラッシュし、期待形が読み取れないまま workflow が落ちた。

## ゲートの実行

### 前景で完走させ、exit code だけを判定根拠にする（サブエージェント向け）

2026-07-25 実戦観測。refine の入口ゲート確認が全量スイート（数分）の完了を待たずに
green=false を返し、原因のない偽 blocked でレビュー結果ごと捨てた。impl 側では偽の赤が
不要な修正ディスパッチを起動し、存在しない原因を探させた。未完走の報告はスクリプトが
1 回だけ再実行して赤を確定させる。

### ゲートは非対話のシェルコマンドに限定する（plan の割り当て）

2026-07-23 実戦観測。plan のゲートに他工程の workflow 実行（review-loop 等）が書かれて
いると、サブエージェントは Workflow ツールを持たないため構造的に実行不能になった。

## resume（キャッシュ再生機構）を使わない

2026-07-08 実測（dandori-review）。workflow のプロンプトは同一 args なら不変のため、
resume では全エージェント呼び出しがキャッシュ再生され、ディスク（台帳・spec/design）を
読み直さずに停止時の結果をそのまま返した — 13ms・トークン 0 で旧ラウンドの
`needs_adjudication` が再返却された。継続状態はディスクが保持しているので、
新規実行の入口確認が次ラウンドを導出するのが正しい再開手段。

## 状態モデル

### モデルブロック・Covers の執筆前に付録を読む（実例から構文を逆算しない）

2026-07-13 実証（cart-product-ops）。既存 spec の実例は正準の部分集合しか見せないため、
Covers 53 行を誤構文で書き、機械検査で初めて気づくことになった。

### シナリオフロー図は 1 シナリオ 1 図に限る（モデル全体の関係図を描かない）

2026-07-08 実験（`experiments/state-model/per-scenario-sample.md`）。関係の整合は
チェッカーの領分で、人間の意思決定に効くのは「シナリオを頭で歩く」シミュレーションの
外部化だけだった。

### 散文レビューの上限（機械検査層の根拠）

23 ラウンドの独立レビューを通過した spec（cart-payment、830 行）に対して、状態変数の
直積を走査する機械検査が実質的な新規指摘を 6 件出した — 宣言済み交点の未カバー×2、
制約矛盾×1、ペア全数性×2、軸混在の未検討×1。一次情報は
`experiments/state-model/findings.md`。

## formatter の .dandori 侵食

ec-replace で 3 例実測。markdown の `_` / `*` を強調として正規化する formatter が、
軸キー（`c_init` → `c*init`）や台帳の軸値表記（`aco_*` → `a*cart`）を破壊し、
チェッカーの typo 誤検出・escalated 誤駆動を生んだ。doctor が probe で実際に確かめる。
